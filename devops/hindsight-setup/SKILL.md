# Hindsight Agent Memory — Setup & Troubleshooting

## When to Use
- Setting up Hindsight for the first time
- Hindsight API crashes or fails to start
- `hindsight-embed` CLI fails with dependency resolution errors
- Migrating from local embeddings to remote providers

## Architecture

Hindsight has two components:
1. **hindsight-api** — The API server (works on any platform with correct providers)
2. **hindsight-embed** — The CLI client (uses `uv` runtime dependency resolution that may pull platform-incompatible deps)

The API server is the important part. The embed CLI is optional — Hermes tools (`hindsight_recall`, `hindsight_retain`, `hindsight_reflect`) call the HTTP API directly.

## Quick Health Check

```bash
curl -s http://localhost:9177/health
# Expected: {"status":"healthy","database":"connected"}
```

## Configuration

### ⚠️ CRITICAL: There are TWO config files. Edit the right one.

The runtime source of truth is **`~/.hermes/hindsight/config.json`** — NOT `~/.hermes/config.yaml`. The plugin's `_load_config()` reads from `config.json` only; the `memory:` section of `config.yaml` is consumed *once* at initial setup (`hermes config memory hindsight`, function `post_setup`) and then written into `config.json`. After that, edits to `config.yaml`'s memory section have **no effect** until you re-run setup.

**Actual configuration flow:**

```
              Initial setup ONLY
              ────────────────────
              config.yaml (memory section)
                       │
                       ▼
              post_setup() writes
                       │
                       ▼
       ~/.hermes/hindsight/config.json   ← RUNTIME SOURCE OF TRUTH — edit this
                       │
                       │ (every Hermes session)
                       ▼
       _materialize_embedded_profile_env()
            + HINDSIGHT_LLM_API_KEY from ~/.hermes/.env
                       │
                       ▼
       ~/.hindsight/profiles/hermes.env  ← AUTO-GENERATED — don't edit
                       │
                       │ (every daemon start)
                       ▼
               hindsight-api daemon
```

**Boot path (no Hermes running):** the launchd agent
`~/Library/LaunchAgents/com.hindsight.daemon.plist` (`RunAtLoad: true,
KeepAlive: true`) auto-starts the daemon on login by running
`~/.hermes/scripts/hindsight-daemon.sh start`. The daemon script just
sources whatever `~/.hindsight/profiles/hermes.env` is on disk — so for
the reboot path to work, **the env file must be correct on disk**.
That's only true if the last Hermes session's regen produced a healthy
env, which in turn requires `config.json` to be correct.

**To change LLM provider/model durably:** edit
`~/.hermes/hindsight/config.json` directly, then run
`bash ~/.hermes/scripts/hindsight-daemon.sh restart` — the daemon script
doesn't regenerate the env on its own, so also do
`python3 -c "import sys; sys.path.insert(0,'/Users/<you>/.hermes/hermes-agent');
from plugins.memory.hindsight import _load_config, _materialize_embedded_profile_env;
_materialize_embedded_profile_env(_load_config())"` first (this is what
Hermes' next start would do anyway). API key still comes from
`~/.hermes/.env` `HINDSIGHT_LLM_API_KEY`, so make sure that env var is
loaded into your shell (`set -a; source ~/.hermes/.env; set +a`).

**Sample working `~/.hermes/hindsight/config.json` for DeepSeek:**
```json
{
  "mode": "local_embedded",
  "llm_provider": "openai_compatible",
  "llm_model": "deepseek-v4-flash",
  "llm_base_url": "https://api.deepseek.com/v1",
  "bank_id": "hermes",
  "recall_budget": "mid",
  "timeout": 120,
  "idle_timeout": 300
}
```

**What Hermes does NOT manage** (set in daemon script or via `export` before launch):
- `HINDSIGHT_API_EMBEDDINGS_LOCAL_MODEL` — local embedding model name
- `HINDSIGHT_API_EMBEDDINGS_PROVIDER` — embedding provider
- `HINDSIGHT_API_RERANKER_PROVIDER` — reranker provider

**API key** — set in `~/.hermes/.env` as `HINDSIGHT_LLM_API_KEY=<key>`. The plugin reads this from `os.environ` (Hermes loads `.env` via `dotenv.load_dotenv`) and writes it into the profile env. Never put the key directly in the profile env file — it will be overwritten on next regen.

### Env File Location
`~/.hindsight/profiles/hermes.env`

Generated by Hermes. Read-only from a troubleshooting perspective. Use `~/.hermes/hindsight/config.json` + `~/.hermes/.env` to make changes.

### Pattern A: Gemini + Google embeddings (original)

```bash
HINDSIGHT_API_LLM_PROVIDER=gemini
HINDSIGHT_API_LLM_API_KEY=<your-gemini-api-key>
HINDSIGHT_API_LLM_MODEL=gemini-2.5-flash
HINDSIGHT_API_LOG_LEVEL=info
HINDSIGHT_API_EMBEDDINGS_PROVIDER=google
HINDSIGHT_API_EMBEDDINGS_GEMINI_MODEL=gemini-embedding-001
HINDSIGHT_API_RERANKER_PROVIDER=rrf
```

### Pattern B: Any OpenAI-compatible API (DeepSeek, OpenRouter, etc.)

Use provider=`openai` + set `HINDSIGHT_API_LLM_BASE_URL` to the API's base:

```bash
HINDSIGHT_API_LLM_PROVIDER=openai                  # NOT "deepseek" — unrecognized
HINDSIGHT_API_LLM_API_KEY=<your-api-key>
HINDSIGHT_API_LLM_MODEL=deepseek-v4-flash
HINDSIGHT_API_LLM_BASE_URL=https://api.deepseek.com/v1
HINDSIGHT_API_LOG_LEVEL=info
```

Only these provider names are recognized by the OpenAI-compatible LLM backend: `openai`, `groq`, `ollama`, `lmstudio`, `minimax`, `volcano`, `openrouter`. For any other OpenAI-compatible API (DeepSeek, Together, Fireworks, etc.), use `openai` + a custom `HINDSIGHT_API_LLM_BASE_URL`.

### Pattern C: Remote LLM + local embeddings (no API key for embedding)

The local embedding provider works on Intel Mac when NumPy <2.0 is installed:

```bash
HINDSIGHT_API_LLM_PROVIDER=openai
HINDSIGHT_API_LLM_API_KEY=<your-api-key>
HINDSIGHT_API_LLM_MODEL=deepseek-v4-flash
HINDSIGHT_API_LLM_BASE_URL=https://api.deepseek.com/v1
HINDSIGHT_API_EMBEDDINGS_LOCAL_MODEL=BAAI/bge-base-en-v1.5   # 768-dim (matches Google embedding size)
HINDSIGHT_API_LOG_LEVEL=info
```

The default local embedding model is `BAAI/bge-small-en-v1.5` (384-dim). This will fail with a dimension mismatch if the database was previously using 768-dim embeddings. Use `bge-base-en-v1.5` (768-dim) or `bge-large-en-v1.5` (1024-dim) to match.

### Provider Name Pitfalls

| What you want | Correct provider name | Wrong name | Why wrong |
|---|---|---|---|
| Gemini embeddings | `google` | `gemini` | `gemini` is not a valid embeddings provider — only `local`, `tei`, `openai`, `cohere`, `google`, `litellm`, `litellm-sdk` |
| Gemini LLM | `gemini` | `google` | LLM provider namespace is different from embeddings |
| No reranking | `rrf` | `none` or `disabled` | `rrf` is the passthrough provider (RRF scoring without neural reranking) |

## Common Failure Modes

### 1. `litellm` embeddings — "Failed to connect to LiteLLM proxy at localhost:4000"

The `litellm` embeddings provider expects a **running LiteLLM proxy server** at `http://localhost:4000`. It does NOT make direct API calls.

**Fix:** Use `google` provider instead, which calls the Gemini API directly with the same API key.

### 2. Reranker `local` — NumPy 2.x / torch crash

```
RuntimeError: Failed to connect to LiteLLM proxy at http://localhost:4000
A module that was compiled using NumPy 1.x cannot be run in NumPy 2.4.4
```

The `local` reranker loads `sentence_transformers` → `torch`, which may crash on Intel Mac due to NumPy version mismatch.

**Fix:** Set `HINDSIGHT_API_RERANKER_PROVIDER=rrf` to disable neural reranking.

### 3. Local embeddings — NumPy `_ARRAY_API` / thread-pool crash

```
RuntimeError: Numpy is not available
Exception: Failed to generate batch embeddings: Numpy is not available
```

PyTorch 2.2.2 is incompatible with NumPy 2.x. When `convert_to_numpy=True` is used inside a thread pool (`run_in_executor`), the `.numpy()` call on tensors fails with "Numpy is not available" — even though NumPy works fine from the main thread.

**Fix (two steps):**

1. Downgrade NumPy: `pip install 'numpy<2'`
2. Patch `hindsight_api/engine/embeddings.py` line 207 — change `convert_to_numpy=True` to `convert_to_numpy=False`. The downstream `.tolist()` call works identically on tensors.

This allows `local` embeddings AND `local` reranker to work on Intel Mac — no need to disable them.

### 4. CrossEncoder — `model_kwargs` renamed to `automodel_args`

```
TypeError: CrossEncoder.__init__() got an unexpected keyword argument 'model_kwargs'
```

Newer versions of `sentence-transformers` renamed the parameter. The `local` reranker crashes at init.

**Fix:** Patch `hindsight_api/engine/cross_encoder.py` line 235 — change `model_kwargs=` to `automodel_args=`.

### 5. Embedding dimension mismatch on existing data

```
Embedding dimension mismatch on memory_units: database has 768, model requires 384
Cannot change embedding dimension from 768 to 384: memory_units table contains 1237 rows
```

The default local model (`BAAI/bge-small-en-v1.5`) produces 384-dim vectors. If the database was previously using 768-dim embeddings (Google `text-embedding-004` or similar), this fails.

**Fix:** Set `HINDSIGHT_API_EMBEDDINGS_LOCAL_MODEL=BAAI/bge-base-en-v1.5` (768-dim) to match existing data. No data loss, no re-embedding needed.

Local models and their dimensions:
| Model | Dimensions |
|-------|-----------|
| `BAAI/bge-small-en-v1.5` (default) | 384 |
| `BAAI/bge-base-en-v1.5` | 768 |
| `BAAI/bge-large-en-v1.5` | 1024 |

When migrating from Google embeddings, `bge-base` (768) matches the 768-dim format.

### 6. `hindsight-embed` CLI fails — "uv resolves [all] extras requiring MLX"

The embed CLI uses `uv` for runtime dependency resolution which pulls `[all]` extras including MLX (Apple Silicon only). This makes the entire CLI unusable on Intel Mac.

**Fix:** Use the HTTP API directly (port 9177) or the daemon wrapper script. The Hermes agent tools already do this.

### 7. Duplicate daemon processes from restart loops

```
ps aux | grep hindsight-api  →  two or more processes on port 9177
```

Caused by: starting the daemon while an existing process is still initializing (model download in progress). The old daemon script (v1, 15s timeout) would report failure, a new `start` would spawn a second process, and both would compete for port 9177.

**Fix:** Use v2 daemon script (`restart` command, which stops before starting). If duplicates exist, run `stop` first to clean up all processes on the port, then `start`.

### 8. Env file reverts after manual edit

```
I wrote the env file with DeepSeek settings but after restart it shows gemini again.
```

**Root cause:** Hermes's Hindsight memory plugin calls `_materialize_embedded_profile_env()` on every Hermes startup, which regenerates the env file from `config.yaml` memory section + `~/.hermes/.env`. Any manual edits are lost.

**Fix:** Configure through the proper channels:
- `config.yaml` memory section: `llm_provider`, `llm_model`, `llm_base_url`
- `~/.hermes/.env`: `HINDSIGHT_LLM_API_KEY`
- Daemon script variable: `EMBEDDINGS_MODEL` (for `HINDSIGHT_API_EMBEDDINGS_LOCAL_MODEL`)

Never edit `~/.hindsight/profiles/hermes.env` directly — it's an auto-generated file.

## Daemon Wrapper

A wrapper script at `~/.hermes/scripts/hindsight-daemon.sh` provides start/stop/restart/status:

```bash
bash ~/.hermes/scripts/hindsight-daemon.sh start    # Starts API, waits up to 60s for health
bash ~/.hermes/scripts/hindsight-daemon.sh status   # Shows PID, health, DB sizes, log size
bash ~/.hermes/scripts/hindsight-daemon.sh stop     # Graceful + force-kill fallback
bash ~/.hermes/scripts/hindsight-daemon.sh restart  # stop → wait 2s → start
```

Key design decisions (v2):
- **60s health-check loop** — polls every 2s for 30 attempts. Handles first-time model downloads (bge-base is ~400MB). If still not healthy after 60s but process is alive, reports "Process alive but not yet healthy" instead of erroring.
- **Embedding config injection** — sets `HINDSIGHT_API_EMBEDDINGS_LOCAL_MODEL` explicitly (Hermes plugin doesn't manage this). Edit the `EMBEDDINGS_MODEL` variable at the top of the script to change.
- **Port-scan fallback for stop** — finds hindsight-api processes on port 9177 regardless of PID file state. Handles stale PID files and zombie processes.
- **Auto log truncation** — if `hermes.log` > 100MB, truncates to a single timestamp line on start. The log can accumulate hundreds of MB from repeated crash-restart loops.
- **PID file repair** — `status` and `stop` scan for running processes and repair the PID file if it was cleaned up or stale.
- **No `--daemon` flag** — runs API directly under `nohup`.

## Starting the API Manually

```bash
set -a; source ~/.hindsight/profiles/hermes.env; set +a
~/.hermes/hermes-agent/venv/bin/hindsight-api --port 9177
```

## Verifying Startup

Check the log for these lines:
```
Embeddings: provider=google
Reranker: provider=rrf
Application startup complete.
Uvicorn running on http://0.0.0.0:9177
```

If you see `Application startup failed. Exiting.` — check the log above for the specific error.
